In this project you go back to the touchscreen of the DE2-115 board and implement **touch position detection**. To do so, you design a serial communication interface with the external analogue-to-digital converter that reads the position. You finish with a physical verification of the design using the **SignalTap** embedded logic analyser, to check that the converter behaves as expected.

## Goals

- Understand how a serial interface works.
- Design communication interfaces.
- Design systems based on a *control path* and a *datapath*.
- Write testbenches based on functional models.
- Debug circuits during operation using SignalTap.

## Work to be done

- **Part 1:** circuit (ADC_CONTROL), verification with the provided testbench, and modification of the testbench to add the requested extra cases.
- **Part 2:** circuit including the 7-segment decoding, on-board test, and SignalTap tests (one capture and several captures).
- **Part 3:** circuit, verification with the provided testbench, and on-board test.
- **Project report**, including the *RTL Viewer* and *State Machine Viewer* results, the analysis/synthesis warnings report and the commented test.

## Introduction

### Contact position readout

![[assets/diseno-de-una-comunicacion-serie/pantalla-tactil-ltm/imagen042.png]]

This project uses the same touchscreen as [[sdp/en/project2-video-controller|Project 2]]. Display and touch capture are completely independent, so you can use only the touch capture without displaying anything, as you will do here.

![[assets/diseno-de-una-comunicacion-serie/estructura-pantalla-tactil-ltm/imagen043.png]]

Touch capture is handled by an analogue-to-digital converter (**ADC**) connected to the screen: an Analog Devices **AD7843**, a **12-bit** ADC. It obtains the X and Y coordinates of the touched point, 12 bits each, and has a serial interface through which their values are read.

![[assets/diseno-de-una-comunicacion-serie/caracteristicas-_touch_/imagen044.png]]

The screen connection has two serial interfaces: one for the screen (display) and one for the ADC (touch point). Both reach the FPGA through a 40-pin expansion connector and, because of the limited number of pins, they share some signals: the same clock (**ADC_DCLK**) and the same enable (**SCEN**). So that communication with one device does not interfere with the other, the ADC's enable goes through an inverter: when the LCD is enabled (SCEN low) the ADC is disabled, and vice versa.

Besides these two shared lines, the ADC's serial interface has:

- **ADC_DIN**, data input line used to send management and control commands to the ADC;
- **ADC_DOUT**, data output line through which the ADC sends the 12 bits of each coordinate serially;
- **ADC_BUSY**, used by the ADC to indicate that it is busy;
- **ADC_PENIRQ_n**, interrupt request generated by the ADC when the screen is touched.

### Timing diagram

![[assets/diseno-de-una-comunicacion-serie/diagrama-de-temporizacion/imagen047.png]]

The figure shows the timing diagram of the ADC communication protocol for reading the X or the Y coordinate. The FPGA starts the communication as **master** and the ADC acts as **slave**. The FPGA generates the **SCEN** select signal, the **ADC_DIN** signal carrying the command that requests the coordinate, and the **ADC_DCLK** signal, which sets the communication speed and synchronises the bits on ADC_DIN and ADC_DOUT. The remaining signals (ADC_DOUT, ADC_PENIRQ_n and ADC_BUSY) are generated by the ADC and read by the FPGA.

![[assets/diseno-de-una-comunicacion-serie/diagrama-de-temporizacion/imagen053.png]]

Although the FPGA controls the communication, it needs to know when to start it: when the screen is touched. The ADC signals this with **ADC_PENIRQ_n**, which is normally high and goes low when the screen is touched with a finger or a pen. The FPGA must monitor this signal and start the serial communication when it goes to 0.

Communication begins by activating SCEN and generating ADC_DCLK and ADC_DIN as in the diagram. A **control command** requesting the X or Y coordinate is sent on ADC_DIN; the following table gives the bits of each command. After receiving it, the ADC performs the conversion and sends the 12 bits of the coordinate serially on **ADC_DOUT**, synchronised with ADC_DCLK. Since each coordinate needs a different command, the process is repeated twice: once for X and once for Y.

![[assets/diseno-de-una-comunicacion-serie/diagrama-de-temporizacion/imagen055.png]]

ADC_DIN must stay low whenever no command is being transmitted.

> [!warning] ADC_DCLK is not a clock
> Despite its name, ADC_DCLK is not really a clock signal: it is low while idle and only toggles during communication, setting the speed and synchronising the bits. Each transmission-reception sequence for one coordinate lasts **24 periods** of ADC_DCLK. The ADC accepts periods between **0.5 μs and 0.1 ms**, i.e. speeds between **10 kbps and 2 Mbps**.

![[assets/diseno-de-una-comunicacion-serie/diagrama-de-temporizacion/imagen054.png]]

## Part 1: Design of the serial interface

![[assets/diseno-de-una-comunicacion-serie/subtarea-1-interface-serie-del-convertidor-adc/imagen045.png]]

In the first part you design the serial communication interface with the ADC to obtain the X and Y coordinates of the touch point, following the AD7843 timing. The block has a clock input for the **50 MHz** oscillator, an asynchronous active-low reset, the signals to communicate with the ADC, and two **12-bit** output buses, one per coordinate.

Although the clock runs at 50 MHz, the communication speed must be between 10 kbps and 2 Mbps. **70 kbps** is proposed as a reference value.

To help with the design and its verification, an archived Quartus project is provided, [[assets/diseno-de-una-comunicacion-serie/plantilla_proyecto_4.qar|Plantilla_Proyecto_4.qar]], containing a template of the **ADC_CONTROL.v** module with its ports already defined, which you must complete or replace with your design. The project also contains the verification files and is fully configured, so we recommend starting from it rather than creating the circuit from scratch.

### Suggestion: half-cycle counter

![[assets/diseno-de-una-comunicacion-serie/sugerencia-contador-semiciclos/imagen048.png]]

We suggest using a counter that counts the **half-periods** of ADC_DCLK needed to complete the transmission-reception sequence. Each coordinate's sequence lasts 24 periods, i.e. **48 half-periods**, so a **modulo-48** counter would be needed. The figure adds this count to the timing diagram: its value is used to generate ADC_DCLK and ADC_DIN and to capture the bits received on ADC_DOUT.

![[assets/diseno-de-una-comunicacion-serie/sugerencia-contador-semiciclos/imagen056.png]]

ADC_DCLK changes value every half-period. ADC_DIN must change at the right moment, on the **falling edges** of ADC_DCLK, as shown in the figure. For example, bit A0 is placed on ADC_DIN when the count changes from 5 to 6 and is held during counts 6 and 7.

![[assets/diseno-de-una-comunicacion-serie/sugerencia-contador-semiciclos/imagen057.png]]

The bits sent by the ADC on ADC_DOUT must be captured in the **middle** of each bit, where the line is most stable. For example, bit 9 is captured when the count changes from 22 to 23, bit 8 between counts 24 and 25, and so on. These captures coincide with the rising edges of ADC_DCLK, but the reference for them is not that edge but the **counter value**, as for the other signals.

### Suggestion: readout concatenation

![[assets/diseno-de-una-comunicacion-serie/sugerencia-concatenacion/imagen058.png]]

Reading X and Y requires two consecutive transmission-reception sequences. However, the timing diagram shows ADC waiting times inside each sequence, so the process can be sped up by combining both into a single sequence that uses those waits to request the next data.

![[assets/diseno-de-una-comunicacion-serie/sugerencia-concatenacion/imagen059.png]]

In the concatenated sequence of the figure, the request for the Y coordinate starts while X is still being received; this is possible because the transmit and receive lines are independent. The combined sequence takes only **80 half-periods**, instead of the 48 + 48 = 96 of two separate communications.

<iframe src="https://rutorcu-upvnet.github.io/SDPmuise/static/animaciones/diseno-de-una-comunicacion-serie/sugerencia-concatenacion/Temporizacion_Tactil01.html" width="720" height="400" style="border:0;max-width:100%"></iframe>

Here again is the table with the commands to send to the ADC to read the X and Y coordinates:

![[assets/diseno-de-una-comunicacion-serie/diagrama-de-temporizacion/imagen055.png]]

> [!question]- With a 50 MHz clock and 70 kbps as reference, what modulus should the ADC_DCLK_CNT divider have?
>> [!todo] At 70 kbps each bit (one ADC_DCLK period) lasts about 14.3 μs, and each half-period about 7.14 μs, i.e. about 357 cycles at 50 MHz. The exact value depends on how your design generates ADC_DCLK; any value that keeps the speed between 10 kbps and 2 Mbps is valid.

### Proposed design structure

Building on the idea of concatenating the two sequences, the following block diagram is proposed as a guide. It is a **synchronous design**: all blocks share the 50 MHz clock and the asynchronous reset.

<iframe src="https://rutorcu-upvnet.github.io/SDPmuise/static/animaciones/diseno-de-una-comunicacion-serie/propuesta-estructura-diseno/diagrama_bloques_2024/Diagrama_bloques_bi_sin_half.html" width="720" height="400" style="border:0;max-width:100%"></iframe>

The schematic has the following blocks:

- On the left, a counter with modulus **ADC_DCLK_CNT** (a parameter) that acts as a frequency divider and sets the transmission speed between 10 kbps and 2 Mbps, for example 70 kbps. You can use the counter from [[sdp/en/project1-lighting-effect|Project 1]].
- In the centre, a **modulo-80** counter that is the reference for the 80 half-periods of the sequence reading both coordinates. Again, our old reliable counter will do.
- Below, in yellow, the block that generates **ADC_DCLK**, from the half-period count and/or the TC signal of the first counter.
- On the right, the block that generates **ADC_DIN** from the half-period count.
- Just below, the block that **captures the ADC_DOUT bits**, using the half-period count and, as enable, the terminal count of the first counter.
- At the top, a **state machine** that controls the whole design by generating the necessary enable signals. It starts the communication from **ADC_PENIRQ_n** and generates the **SCEN** select signal.

In this proposal, the **ADC_BUSY line is not used**.

### Proposed state machine

The state machine that manages the protocol is not unique; it can be designed in several ways. One proposal is shown here, in two equivalent representations (ASM chart and state diagram):

![[assets/diseno-de-una-comunicacion-serie/propuesta-fsm/imagen060.png]]

It is a four-state machine:

- **S0**: initial state after reset. It is transitory and only initialises the signals.
- **S1**: waits for the screen to be touched, i.e. stays while ADC_PENIRQ_n is 1. When it goes to 0, the machine moves to S2.
- **S2**: starts the protocol by activating the enables (counters and converter select). It stays here until X and Y have been read, which is marked by the 80 half-periods counted by the modulo-80 counter.
- **S3**: transition state that ends the communication and signals it with **Fin_Trans**.

### Functional verification

![[assets/diseno-de-una-comunicacion-serie/verificacion-del-diseno/imagen061.png]]

Once the interface is described in Verilog, it must be verified functionally by simulation. Generating the converter signals at low level or with a stimulus editor is not easy, so it is better to raise the test to a higher level of abstraction: a **functional model** of the touchscreen that emulates the ADC communication, in the file **EMULE_ADC.vo**, is used by a Verilog testbench simulated in ModelSim.

#### Testbench structure

The verification environment in the Quartus project has the structure shown in the figure. The top-level file, **tb_Touch_Control.v**, is a structural description that instantiates and connects the other blocks:

- **ADC_CONTROL.v**: your design, the target of the verification.
- **EMULE_ADC.vo**: emulator (functional model) of the screen, which simulates the ADC's behaviour.
- **MFB.v**: functional bus model, which generates the basic signals (clock and reset) and provides the interface to simulate a communication and check whether it is correct.

As usual, tb_Touch_Control has no inputs or outputs.

<iframe src="https://rutorcu-upvnet.github.io/SDPmuise/static/animaciones/diseno-de-una-comunicacion-serie/verificacion-del-diseno/diagrama_verificacion_bi/Diagrama_verificacion_bi.html" width="720" height="400" style="border:0;max-width:100%"></iframe>

The MFB generates the clock and reset. It also implements a *task* that simulates a touch: it gives X and Y coordinates to the emulator and activates **NEW_COORD** so that the emulation starts. The emulator then drives ADC_PENIRQ_n low, and ADC_CONTROL must respond by starting the communication, in which it receives the coordinates the MFB gave to the emulator. When ADC_CONTROL has obtained X and Y, the MFB compares them with the originals and prints on the ModelSim console whether the verification is correct.

#### Checking your design

![[assets/diseno-de-una-comunicacion-serie/comprobacion/captura_11_may_2024.png]]

When the simulation runs in ModelSim, it emulates the reception of a pair of coordinates fixed in the testbench code. If they are received correctly, the console shows the message **"Verificación del DUV correcta"** (correct DUV verification).

![[assets/diseno-de-una-comunicacion-serie/comprobacion/imagen034.png]]

If it does not appear, there is a problem in the design. For example:

- **The simulation does not start** because ModelSim found an error in ADC_CONTROL that Quartus let through. Fix it in Quartus and run the simulation again.
- **The simulation starts but never ends.** ADC_CONTROL does not work, usually because the communication never finishes: its signals do not return to their idle values.
- **The simulation ends with the message "Error de Transmisión"** (transmission error). The received coordinates do not match the ones sent, so ADC_CONTROL has an error.

#### Testbench modification

Once ADC_CONTROL passes the initial simulation, extend the verification by modifying **tb_Touch_Control.v** to add two new cases:

1. **CASO 2**: three consecutive communications with three different data values, without activating reset between them. The coordinate values can be fixed in the code. Add this case from line 96 of the file, under the `CASO 2` comment, using the `CASO 1` lines as a reference but **without `MFB.reset`**.
2. **CASO 3**: another three consecutive communications, now with **random** coordinates instead of fixed ones. Add it under the `CASO 3` comment. We recommend using the `$random` function and the `repeat` construct.

Once the verification is correct, you can move on to the physical verification.

## Part 2: Physical verification

![[assets/diseno-de-una-comunicacion-serie/subtarea-2-visualizacion-del-punto-de-contacto-de-la-pantalla/imagen052.png]]

The second part tests ADC_CONTROL on the DE2-115 board with the touchscreen. The X and Y coordinates of the touch point are obtained and shown on the **7-segment displays** in hexadecimal, 12 bits per coordinate. The figure shows the extreme coordinate values at each corner.

![[assets/diseno-de-una-comunicacion-serie/subtarea-2-visualizacion-del-punto-de-contacto-de-la-pantalla/imagen046.png]]

You need to add a block that converts the binary coordinates into the display signals. Design a **7-segment decoder** for a single hexadecimal digit and create a **new top-level module** that instantiates ADC_CONTROL together with several copies of the decoder, so that all bits of both coordinates are translated.

> [!question]- How many copies of the decoder are needed?
>> [!todo] Six: each coordinate has 12 bits, i.e. 3 hexadecimal digits, and there are two coordinates.

You also need to assign the pins that connect to the screen and to the displays:

![[assets/asignaciones_de2_115/captura-de-pantalla-2019-11-05-a-las-15.30.53.png]]

![[assets/asignaciones_de2_115/captura-de-pantalla-2019-11-05-a-las-15.32.44.png]]

Once the serial communication works, finish the verification by checking that the displayed values roughly match the expected ones for each touch point.

> [!note] The corners cannot be reached
> It is practically impossible to see `12'h000` or `12'hFFF` on the display: the touch surface is very small compared to the screen's touch resolution, and the methacrylate frame limits access to the edges. Do not worry if you cannot reach the theoretical extreme values given by the manufacturer.

## Part 3: Design upgrade

During the on-board test you may notice that, while you keep your finger on the screen, the displayed coordinates are stable and roughly correct, and they change sensibly as you drag it. However, **when you lift your finger** the last displayed value changes to a coordinate unrelated to the last position (sometimes only one of the two changes). This happens because, while the screen is touched, the ADC reads the position continuously and, when released, it still makes one last reading with no finger on the screen, so the resistance changes and the coordinate is wrong.

This can be fixed by adjusting two things:

1. **The communication speed**, which can be between 10 kbps and 2 Mbps. In the template it is set by the **ADC_DCLK_CNT** parameter, initially to about 70 kbps. Changing it can reduce the effect, although it may not be enough.
2. **A pause between two consecutive acquisitions**, so that the ADC does not convert continuously. When the screen is touched, one communication is made and no other is started until at least a certain time has passed (for example, half a second), even if the finger stays on the screen. Fewer readings are made and the wrong ones are avoided, at the cost of slightly modifying the design to add an element that generates the wait.

<iframe src="https://rutorcu-upvnet.github.io/SDPmuise/static/animaciones/diseno-de-una-comunicacion-serie/verificacion-y-mejora-del-diseno/diagrama_bloques_2024/Diagrama_bloques_mejora_bi_sin_half.html" width="720" height="400" style="border:0;max-width:100%"></iframe>

To reduce the number of readings, we propose adding a **modulo-25,000,000** counter that introduces a **half-second** delay between one reading and the next; it appears at the bottom left of the new block diagram.

This counter requires changes to the ADC_CONTROL state machine. A simple way is to add a wait state **S4** after the communication has finished and the coordinates have been obtained. In S4 the machine enables the modulo-25,000,000 counter and stays there until it reaches its terminal count. This way no new communication, and therefore no new capture, starts until half a second has passed.

The block diagram shows the machine's new inputs and outputs, and the next figure shows the state diagram with the new state:

![[assets/diseno-de-una-comunicacion-serie/verificacion-y-mejora-del-diseno/imagen065.png]]

> [!tip] Tuning the delay
> The counter modulus can be adjusted afterwards to choose the most suitable delay for the transmission speed.

Verify the upgraded design with the provided testbench and test it on the board.

> [!question]- Why are 25,000,000 cycles half a second?
>> [!todo] With a 50 MHz clock each cycle lasts 20 ns, and 25,000,000 × 20 ns = 0.5 s.
